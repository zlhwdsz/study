# sync.Cond 简介

`Cond` 不记录通知次数，也不保证每个`Signal` 都对应一次处理。`Cond` 必须配合一个共享条件一起用，而不能单独把`Signal` 当消息。

`sync.Cond` ：
- 条件满足时不用睡觉，直接继续。
- 条件不满足时让 goroutine 睡觉，条件可能满足时把它叫醒。

关键点是：`Cond` 本身不保存条件。真正的条件是你自己的共享变量，比如`len(queue) > 0` 、`mailbox == 1` 、`ready == true` 。`Cond` 只负责等待队列和唤醒通知。

sync.Cond 并不是开箱即用的，只能利用 sync.NewCond 函数来创建它的指针值。

条件变量与互斥锁的关系：sync.Cond 含有一个 L Locker 字段，一般传入互斥锁类型。

读锁初始化`Cond` 适合的场景很窄：等待方醒来后只读取某个状态，不修改它；状态变化由其他 goroutine 持写锁完成；并且你能接受多个等待方同时通过条件检查。

# sync.Cond 典型写法

```go
// 等待方
mu.Lock()
for 条件不满足 {
    cond.Wait()
}
处理共享状态
mu.Unlock()

// 修改方
mu.Lock()
修改共享状态
cond.Signal() 或 cond.Broadcast()
mu.Unlock()
```

比如：

```go
var mu sync.Mutex
cond := sync.NewCond(&mu)

queue := make([]int, 0)

// 消费者
mu.Lock()
for len(queue) == 0 { // 必须持锁：检查条件
    cond.Wait() // 必须持锁：Wait()
}
item := queue[0] // 必须持锁：修改条件
queue = queue[1:]
mu.Unlock()

_ = item

// 生产者
mu.Lock()
queue = append(queue, 1) // 必须持锁：修改条件
cond.Signal() // 不强制持锁：Signal()，Broadcast()。
mu.Unlock()
```

# sync.Cond 一些知识点

## 正确的心智模型

`sync.Cond` 的正确心智模型不是：
> 我必须收到一次 Signal 才能继续。
而是：
> 我只关心条件是否成立；Signal 只是提醒我“条件可能变了，醒来重新看一眼”。

## Wait

Wait: 当前 goroutine 在等待状态中不持锁，但醒来时会再次抢锁！
```go
func (c *Cond) Wait() {
	c.checker.check()
	t := runtime_notifyListAdd(&c.notify) // 将当前 gorouine 加入到当前条件变量的通知队伍中。
	c.L.Unlock() // 解锁。（所以 Wait 必须在锁内执行!）
	runtime_notifyListWait(&c.notify, t) // 让当前 goroutine 处于等待状态，直到通知到来且决定唤醒当前 goroutine。
	c.L.Lock() // 上锁并返回。
}
```

## 持锁检查

典型写法中，持锁检查，没有“检查完条件”和“进入 Wait”之间的空窗期：消费者检查`ready` 时持有锁，生产者无法同时修改；消费者调用`Wait()` 时，`Wait()` 会把“加入等待队列 + 释放锁”作为一个原子（并发语义上的原子性）过程处理，所以不会漏掉通知。

```go
// 错误示例
if !ready {        // 没有持锁检查
    mu.Lock()
    cond.Wait()
    mu.Unlock()
}
```

可能发生这种时序：
```text
消费者：看到 ready == false
生产者：mu.Lock()
生产者：ready = true
生产者：cond.Signal()  // 此时还没人 Wait，通知丢了。
生产者：mu.Unlock()
消费者：mu.Lock()
消费者：cond.Wait()    // 开始睡，但既不会等到感知条件成立，也不会接到通知了。
```

但若持锁检查：
- 要么消费者先拿到锁，检查条件后开始睡眠，且不会错过生产者发出的通知。
- 要么生产者先拿到锁，修改条件后发出的通知丢了，但条件已经留下来了。紧接着拿到锁的消费者检查条件后，根本就不会进入睡眠等待。

## for ? if ？

`Wait()` 返回只代表“有人通知过”，不代表“当前条件一定成立”。可能有多个消费者被唤醒（Broadcast），也可能其中一个先抢到锁把数据消费掉，后面的 goroutine 重新拿到锁时条件又不成立了。所以醒来后要再次检查条件。

- 用 if: 只有”检查条件“与 Wait 在同一把锁内，而 Wait 返回后的”修改条件“则没有”检查条件“护航，继续执行可能会造成逻辑错误。
- 用 for: Wait 返回后的”修改条件“也有前置的、在同一把锁内的”检查条件“。

## Signal / Brodacast

Signal: 唤醒等待最久的 goroutine。

Brodacast: 唤醒所有在等待的 goroutine。

注意：条件变量的通知具有**即时性**，而不会保被保存：如果发送通知的时候没有 goroutine 为此等待，那么该通知就会被直接丢弃。在这之后才开始等待的 goroutine 只可能被后面的通知唤醒。

Signal / Brodacast 的执行不强制持锁，**但通常会将其放在锁内**，主要是为了让代码更容易推理：状态变化和通知紧挨着发生，不容易写出“通知了但条件还没准备好”或者“条件变化和通知顺序混乱”的代码。

## 适用场景

`sync.Cond` 适合“多个 goroutine 等某个共享状态变化”的场景，比如队列非空、资源池有空闲资源、初始化完成等。简单的一次性通知通常用`channel` 更直观；需要反复等待同一个条件变化时，`sync.Cond` 更贴近问题模型。
