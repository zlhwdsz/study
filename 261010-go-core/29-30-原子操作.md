# 原子性

一些概念上的区别：
- 并发语义上的原子性：互斥锁即能提供，让“使用同一把锁”的多个 goroutine 在一段临界区代码内只能串行执行而不能并行执行。
- 机器指令层面的原子性：
  - 互斥锁保护的临界区内的代码仍然可能被中断，所以互斥锁保证不了机器指令层面的原子性。
  - 原子操作：
    - 执行时在机器指令层面就不会中断。由 CPU 提供底层芯片级别的支持。
    - 针对相同共享资源的原子操作，执行时即使是多 CPU，也只能串行执行，而不会并行。
- 事务：除了原子性，还额外有中途失败后的回滚。

# 原子操作

## 支持的数据类型与操作类型

支持的操作：
- add
- and, or
- cas(compare and swap), swap
- load, store

支持的数据类型：
- int32, int64, uint32, uint64, uintprt
- unsafe.Pointer(缺加法)
- Value(可被用来存储任意类型的值，只支持 load, store, swap, cas 操作)

## 入参传指针

任意支持的类型，传入的第一个参数都应是其指针，包括 unsafe.Pointer 也应传 *unsafe.Pointer 类型。

## 支持减法

对于 int32/int64 类型来说，add 函数第二个参数传负数即可。

对于 uint32/uint64 来说，add 函数第二个参数类型要求也是 uint32/uint64。对于 int/int32 类型的 negative，有两种解决办法：
- 传 `uint32(negative)`；不过当 negative 是负数的常量或字面值时，会编译不通过；若是变量，则会通过编译。
- 传补码 `^uint32(|negative|-1)`，即 `^uint32(-negative-1)`。"^" 作为一元操作符是按位取反，作为二元操作符是按位异或。

## cas vs swap

```go
func SwapInt32(addr *int32, new int32) (old int32)
func CompareAndSwapInt32(addr *int32, old, new int32) (swapped bool)
func AddInt32(addr *int32, delta int32) (new int32)
func AndUint32(addr *uint32, mask uint32) (old uint32)
func OrInt32(addr *int32, mask int32) (old int32)
func LoadInt32(addr *int32) (val int32)
func StoreInt32(addr *int32, val int32)
```

交换：原子性地“赋新返旧”。**`Swap` 与`Store` 的表面差别是`Store` 不返回旧值**；本质差别是`Swap` 把“读旧值 + 写新值”合成一个原子操作。
CAS：有条件的交换操作，只有在条件满足(旧值等于预期值)的情况下才会赋新值。它返回 bool 变量以表明是否真的进行了赋值操作。

## for+cas vs mutex
```go
// cas + for: 实现一种简易的自旋锁（spinlock）。
for {
 if atomic.CompareAndSwapInt32(&num2, 10, 0) {
  fmt.Println("The second number has gone to zero.")
  break
 }
 time.Sleep(time.Millisecond * 500)
}

// 注：严格的自旋锁一般长这样：
var locked int32
// 加锁：从 0 抢成 1
for !atomic.CompareAndSwapInt32(&locked, 0, 1) {
}
// 解锁：改回 0
atomic.StoreInt32(&locked, 0)
```

两种操作的假设对比：
- 使用 for + cas 操作的假设：乐观地认为竞争不严重，或者目标状态很快会出现。失败了就再试，不让 goroutine 阻塞在锁上。
- 使用互斥锁的假设：共享状态需要被一段临界区整体保护，或者竞争较频繁时，与其不断 CAS 重试，不如让 goroutine 阻塞等待锁。

即：
- 逻辑简单、单变量、竞争低：CAS 可以。
- 逻辑复杂、多变量、竞争高：Mutex 通常更稳。

## 原子写，也要原子读

类似读写锁的写操作和读操作之间是互斥的，原子读和写也应互斥。

混用原子写+普通读：如果原子写操作还没有进行完，普通读操作就来读了，那么就只能读到仅修改了一部分(比如只有高位)的值。这显然破坏了值的完整性，读出来的值也是完全错误的。

一旦你决定了要对一个共享资源进行保护，那就要做到完全的保护。不完全的保护基本上与不保护没有什么区别。

## atomic.Value

Go 语言在 1.4 版本发布的时候向sync/atomic包中添加了一个新的类型Value。此类型的值相当于一个容器，可以被用来“原子地”存储和加载任意的值。


atomic.Value 开箱即用。

一旦 atomic.Value 类型的原子值被真正使用（用来存储值），它就不应该再被复制了（新旧值之间没有关系、不会互相影响了）。

关于用原子值来存储值，有两条强制性的使用规则:
- 不能把nil作为参数值传入原子值的Store方法，否则就会引发一个 panic。
- 向原子值存储的第一个值，决定了它今后能且只能存储哪一个类型的值。且是具体类型而不是接口类型。

尽量不要向`atomic.Value` 中存储会被继续修改的引用类型值，例如`map` 、`slice` 、指针指向的可变对象。否则`Load/Store` 虽然是原子的，但对象内部仍可能发生并发读写。如果非要存引用类型：
```go
type Config struct {
    Timeout int
    Hosts   []string
}

var v atomic.Value

var h = []string{"a", "b"}

cfg := Config{
    Timeout: 1000,
    Hosts:   h,
}

// Store 前复制底层数组，把引用字段变成不可共享的快照，避免 atomic.Value 存进去的配置被外部继续修改。
cfg.Hosts = append([]string(nil), cfg.Hosts...) // Go 1.21+: cfg.Hosts = slices.Clone(cfg.Hosts)
v.Store(cfg)


// 更新时不要修改旧对象，而是构造一个新对象再整体替换：
old := v.Load().(Config)

next := Config{
    Timeout: 2000,
    Hosts:   append([]string(nil), old.Hosts...),
}
next.Hosts = append(next.Hosts, "c")

v.Store(next)
```
