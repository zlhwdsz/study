### B+ 树优劣点

B+ 树是一种多路平衡搜索树，常用于数据库索引和文件系统索引。它和普通二叉搜索树相比，核心优势是“树高低、磁盘 IO 少、范围查询友好”。

优点：

1. **树高低，查询 IO 少**：B+ 树的每个节点可以存很多 key，因此分叉数很高，整体高度很低。数据库索引一般存储在磁盘页中，一次读取一个节点就相当于一次页读取，所以树越矮，磁盘 IO 次数越少。
2. **范围查询效率高**：B+ 树的数据都存放在叶子节点，叶子节点之间通常通过链表连接。找到范围起点后，可以沿着叶子节点顺序扫描，非常适合 `between`、`>`、`<`、排序和分页查询。
3. **查询性能稳定**：所有数据都在叶子节点，根到叶子的路径长度基本一致，因此单点查询的路径比较稳定。
4. **更适合磁盘和页缓存**：内部节点只存 key 和子节点指针，不存完整数据，所以一个内部节点能容纳更多 key，进一步降低树高，也更符合数据库按页加载的存储模型。

缺点：

1. **实现复杂**：插入、删除时可能涉及节点分裂、合并、借位、父节点调整，实现比普通二叉树复杂。
2. **写入有维护成本**：为了维持平衡和叶子节点有序，写入、删除会带来额外结构调整；如果是数据库索引，还可能导致页分裂。
3. **点查不一定比哈希快**：如果只做等值查询，哈希索引理论上可以接近 O(1)，B+ 树通常是 O(logN)。但 B+ 树支持范围查询和排序，这是哈希索引不擅长的。
4. **占用额外空间**：需要维护内部节点、叶子链表和指针信息，会有额外存储开销。

面试时可以总结为：B+ 树牺牲了一定的写入维护成本和实现复杂度，换来了低树高、少磁盘 IO、稳定查询和优秀的范围扫描能力，所以非常适合作为数据库索引结构。

页分裂：数据库索引通常按页存储，B+ 树的一个节点通常对应一个页。当向某个叶子页插入新索引记录时，如果这个页已经放不下，就需要申请新页，把原页中的一部分记录移动到新页，再更新父节点的指针和分界 key。这个过程就叫页分裂。

例如原来某个叶子页存了 `[10, 20, 30, 40]`，现在要插入 `25`，但页已经满了，就可能拆成 `[10, 20]` 和 `[25, 30, 40]` 两个页，并让父节点新增一个指向新页的索引项。

页分裂的代价在于：需要申请新页、搬移记录、更新父节点；如果父节点也满了，还可能继续向上分裂。随机插入比顺序插入更容易触发页分裂，也更容易产生页碎片。

## Agent

### 讲一讲 Prompt/Context/Harness Engeneering

这三者可以理解为 Agent 应用里的三层工程：

1. **Prompt Engineering**：控制模型“怎么想、怎么答”。
   - 主要关注 system prompt、任务说明、输出格式、few-shot 示例、约束条件。
   - 例如要求模型先分析再回答、必须输出 JSON、遇到不确定信息要说明假设。
   - **它解决的是单次调用里，如何让模型更稳定地产生符合预期的结果**。

2. **Context Engineering**：控制模型“看到什么信息”。
   - 主要关注上下文组织、**RAG(Retrieval-Augmented Generation) 召回**、文档切片、**历史消息压缩**、关键信息排序。
   - 因为模型能力再强，如果上下文里没有正确事实，或者把关键信息放在噪声中间，也容易答错。
   - **它解决的是如何把正确、相关、低噪声的信息放进模型上下文**。

3. **Harness Engineering**：控制模型“如何被系统调用和约束”。
   - Harness 可以理解为模型外层的运行框架，包括工具调用、状态管理、重试、校验、权限控制、日志、评测、人工确认。
   - 例如模型输出 JSON 后，外层代码做 schema 校验；格式错了就自动修复或重试；执行删除、发布等高风险操作前必须人工确认。
   - **它解决的是模型不可靠时，系统如何兜底，让最终产品表现稳定。**

三者的关系是：Prompt 解决“指令表达”，Context 解决“信息供给”，Harness 解决“工程兜底”。真正可用的 Agent 不能只靠 prompt，而是要把这三层一起做。

### LLM 为何会 lost in the middle ?

`lost in the middle` 指的是：当上下文很长时，LLM 往往更容易利用开头和结尾的信息，而容易忽略放在中间的关键信息。

主要原因有几类：

1. 注意力不是等价阅读。Transformer 虽然理论上能看完整个上下文，但长上下文中 token 很多，模型需要在大量信息里分配注意力，中间信息更容易被稀释。
2. 训练分布有位置偏置。**很多语料和任务的关键信息常出现在开头或结尾**，比如标题、摘要、结论、最新指令，**因此模型会学到一定的首尾偏好**。
3. 长上下文增加干扰。上下文越长，无关信息、重复信息和相似信息越多，模型更容易把中间的局部细节淹没掉。
4. 位置编码和推理链路会影响有效上下文。即使模型支持很长的 context window，也不代表每个位置的信息都能被同等稳定地用于最终回答。

应对方式：

1. 把最关键的约束放在开头和结尾重复强调。
2. 对长文档先做结构化摘要，提取问题相关片段，再让模型回答。
3. 使用 RAG 时不要一次塞太多召回内容，控制 chunk 数量和排序。
4. 对长任务维护显式状态，比如目标、约束、已完成事项、当前阻塞点，而不是依赖模型自己从长上下文中回忆。
